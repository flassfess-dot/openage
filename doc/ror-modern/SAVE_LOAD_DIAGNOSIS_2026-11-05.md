# Длительная загрузка «Мой_Лес!»

## Подтверждённая причина

Загрузка блокирует главный поток на длительное время. Между показом экрана загрузки и возвратом `load_game_from_path()` кадры не обрабатываются: Windows показывает окно как не отвечающее. Повреждения сохранения или бесконечного цикла в восстановлении не обнаружено: оба диагностических запуска закончили восстановление мира и подготовку навигации.

Сохранение: `Мой_Лес!`, tick `180360`, формат архива 8 / checkpoint 4. Распакованное состояние занимает 338 593 668 байт. SHA-256 распакованных данных совпал с записанным в архиве. Диагностика выполнялась на отдельной копии, оригинальный файл не перезаписывался.

## Измерения

Использован PCK из `dist/Rise of Rome HUD Fixes` с поставленной native-библиотекой. Для внешней инструментированной сцены использовался диагностический движок Godot 4.7.2. Это замеры пути загрузки того же пакета, а не проверка готового EXE во всех игровых сценариях. Вызовы загрузчика и сохранённые игровые данные не заменялись фикстурами.

| Участок | Запуск с Vulkan |
| --- | ---: |
| Синхронная предварительная загрузка анимаций | 34,849 с |
| Подготовка исходного состояния автосохранения | 12,874 с |
| Восстановление незавершённого расчёта ИИ | 1,523 с |
| Возврат загрузчика, от начала диагностики | 92,634 с |
| Полная готовность навигации, от начала диагностики | 136,228 с |

В запуске без графики загрузчик вернул успех через 103,254 с, навигация была готова через 122,049 с. Значения зависят от нагрузки машины; важна подтверждённая последовательность блокирующих операций.

## Участки реализации

- `launcher.gd::_load_selected_save()` уступает только один кадр перед синхронным чтением архива и инициализацией сцены.
- `main.gd::_ready()` создаёт стартовый матч через `reset_game()`, хотя при загрузке его вскоре заменяют миром из сохранения. Выполняются лишние bootstrap, подготовка представления и начальное создание состояния автосохранения.
- `match_lifecycle_service.gd::restore()` распаковывает checkpoint, создаёт и восстанавливает мир, историю команд и ИИ на вызывающем потоке.
- `main.gd::load_game_from_path()` вызывает `resource_catalog.prewarm_match_entities()`. В `unit_presentation_registry.gd::prewarm_units()` флаг `prewarming` заставляет `ensure_loaded()` синхронно загружать клипы. Для рабочих запрашиваются все состояния их определения, включая состояния разных видов работ.
- `background_autosave.gd::seed_from()` захватывает checkpoint и вызывает `autosave_process_channel.gd::prepare()`, где большой seed синхронно кодируется и записывается через `FileAccess.store_var()`. Фоновое выполнение последующих автосохранений не делает этот начальный этап фоновым.
- После возврата загрузчика `navigation_loading.gd` дополнительно готовит маски, связность, сведения ИИ и ресурсы. Этот этап уже работает через кадры, однако увеличивает общее ожидание.

## Граница исправления

Исправлять следует процедуру загрузки: исключить создание заменяемого стартового матча, вынести изолированное восстановление данных и кодирование seed из UI-потока, выполнять подготовку графики порциями с обновлением состояния загрузки. Нельзя просто отключить предварительную загрузку всех анимаций: тогда задержки и пропадающие кадры могут появиться при первых приказах после входа в матч.

В этой задаче выполнена диагностика по запросу «разберись в чём дело». Производственный загрузчик и сборка не изменены. Наборы тестов не запускались. Разрешённые пользователем диагностические запуски завершены; стадии и сводка сохранены в `prototype/qa/load-hang-20261105/` (`load-stages-packed.log`, `load-stages-rendered.log`, `diagnosis.json`).
