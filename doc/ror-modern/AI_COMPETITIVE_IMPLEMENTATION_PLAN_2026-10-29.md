# Сильный игровой ИИ: план реализации и непрерывного выполнения

Дата: 2026-10-29, Europe/Moscow. Статус: EXECUTING; запуск авторизован пользователем. Фактические результаты: [AI_COMPETITIVE_RESULTS.md](AI_COMPETITIVE_RESULTS.md).

Исполняемый порядок: AI00 → AI01 → AI02 → AI03 → AI04 → AI05 → AI06 → AI07 → AI08 → AI09 → AI10 → AI11 → AI12. Всего 70 задач. Состояние задач хранится в [AI_COMPETITIVE_EXECUTION_STATE_2026-10-29.json](AI_COMPETITIVE_EXECUTION_STATE_2026-10-29.json). Этот документ определяет работу и приёмку; JSON хранит только её фактическое состояние и ссылки на доказательства.

## 1. Результат и границы

Создать сильного, разнообразного и честного skirmish-соперника для текущих правил проекта: эффективное развитие, осмысленная разведка, контрсостав, боевое микро, согласованные операции, сухопутная и морская игра, командное взаимодействие и поддерживаемые условия победы. Выполнение заканчивается проверенным локальным пакетом игры, воспроизводимыми замерами и отчётом о достигнутой силе.

Это развитие E5 с обязательными проверками E3/E4/E6. Основная архитектура и правила остаются из [общей дорожной карты](../DEVELOPMENT_ROADMAP_ROR_PARITY.md). Улучшение skirmish-ИИ является собственным решением движка, не заявлением о точном повторении ИИ оригинального RoR. `source_campaign_v1` сохраняет свой отдельный маршрут принятия решений и получает только необходимые исправления общих контрактов.

Техническая готовность и сила против людей принимаются отдельно. Автоматические победы над ботами подтверждают результат в указанной арене. Человеческий уровень подтверждается отдельной серией партий людей в этой игре. Отсутствие людей или их реплеев не приостанавливает локальную реализацию, настройку, сборку и техническую приёмку; в итоговом отчёте сохраняется HUMAN_UNMEASURED, пока таких данных нет.

В обязательный объём входят алгоритмы, локальная арена, ограниченная автоматическая настройка, инфраструктура обучаемого ранжирования и проверка его пользы. Масштабное нейросетевое самообучение на GPU оформляется как следующий исследовательский цикл с измеренной стоимостью; покупка вычислений, облачные сервисы и скачивание больших моделей для этого плана не требуются.

## 2. Правила выполнения после запуска

1. После явной команды начать выполнение последовательно исполнять все доступные задачи до AI12. Не запрашивать подтверждение перехода между этапами, обычных правок, регрессионных проверок, настройки и локальной сборки. Пользователь явно поручил выполнение всех этапов; дополнительные согласования переходов не нужны.
2. Сначала зафиксировать текущую рабочую копию, включая относящиеся к игре незакоммиченные изменения. Не использовать `git reset`, `clean`, автоматический stash, чужие коммиты или замену всей рабочей копии. Перед правкой уже изменённого файла сохранить его текущую копию и хеш. Не создавать коммит, PR, публикацию или установку в игровые каталоги без отдельного поручения.
3. Любой этап состоит из вертикальных срезов: контракт → минимальная реализация → реальный сценарий → наблюдаемость → сохранение/повтор → приёмка. Пустые классы, переключатели и модульные заглушки не закрывают задачу.
4. После среза обновлять журнал, JSON состояния, результаты и следующий конкретный шаг. Затем продолжать работу. Переполнение контекста требует восстановления по журналу, а не повторения завершённых этапов или вопроса о продолжении.
5. При функциональной ошибке воспроизвести её, локализовать владельца, исправить и повторить затронутые проверки. Прошедшие проверки не повторять без изменения зависимости. Исторические дефекты отделять от новых по исходному снимку.
6. Для неопределённых алгоритмических решений действуют выбранные ниже значения и алгоритмы. Уточнение у пользователя не является зависимостью. Документировать обоснованное локальное отклонение, если проверка обнаружила более подходящий вариант.
7. На улучшение численных показателей одного кандидата отводится не более трёх циклов «изменение → измерение» без нового причинного объяснения. После этого сохранить лучший прошедший вариант, записать QUALITY_GAP и продолжить независимые задачи. Не ослаблять критерии и не выдавать отвергнутую функцию за принятую. Обязательный незакрытый критерий запрещает общий статус COMPLETE.
8. Ошибку корректности нельзя обходить включением повреждённого компонента. Отключить конкретного кандидата, восстановить ранее прошедший путь и продолжить независимую работу. Зависимые задачи остаются открытыми, пока их контракт не работает. Откат касается только изменений текущего исполнителя.
9. Таймаут партии, падение движка, отсутствие прогресса и ошибка инфраструктуры имеют разные статусы. Не превращать их в победу/ничью и не исключать молча из знаменателя. Повтор инфраструктурного сбоя допускается один раз с сохранением обоих результатов.
10. Объективные блокеры: недоступные необходимые файлы/инструменты, отклонённое разрешение, недостаток диска, конфликт с продолжающимися изменениями тех же файлов, без которых дальнейшая работа невозможна. Сначала выполнить независимую работу и безопасные альтернативы, затем сообщить точный блокер. Сложность задачи, отсутствие человеческих реплеев или локальное отсутствие улучшения сами по себе не требуют остановки всего плана.
11. Во время работы давать краткие содержательные обновления. Длительные процессы запускать с журналом и возможностью проверки прогресса; не держать один непроверяемый блокирующий вызов часами. Завершать только процессы, запущенные текущим исполнителем.

## 3. Неприкосновенные контракты

- ИИ получает только законные наблюдения своей стороны. Чужие ресурсы, очереди, технологии, скрытые пассажиры, неразведанная география и будущие события не доступны планировщику. Оценки скрытого состояния должны иметь происхождение, возраст и неопределённость.
- Все действия проходят общие команды, стоимость, ownership, навигацию и fixed-tick симуляцию. Никаких бесплатных ресурсов, ускорения производства или специальных правил урона для ИИ.
- Общая автономия юнитов игрока и компьютера остаётся общей. Новое микро ИИ работает поверх неё через команды и собственный бюджет приказов.
- Вход фоновой задачи неизменяем. Source/apply граница, порядок сторон и результаты не зависят от частоты рендера, скорости CPU или готовности worker в случайную миллисекунду. Время используется для профиля, не для выбора игрового действия.
- Один владелец задачи юнита; одна общая смета ресурсов, населения, очередей, строителей и резервов на решение. Зарезервированные единицы учитывают фактические полуместа, включая Logistics.
- Все новые долговременные планы, бюджеты реакций, RNG и задания сохраняются и продолжаются. Производные индексы и кэши восстанавливаются. Изменения форматов версионируются централизованно; неизвестная версия отклоняется транзакционно.
- На 2026-10-29 код содержит archive 7, checkpoint 3, replay 4; исторические описания archive 5/checkpoint 2 не являются командой понизить формат. AI00 перечитывает фактические константы перед реализацией.
- Новые универсальные механики не зависят от имени цивилизации или конкретного юнита. Доступность, цены, характеристики и бонусы берутся из действующих каталогов и командных опций. Декларативные цивилизационные предпочтения допустимы.
- Карты, цивилизации, физика, темп игры и правила победы не упрощаются ради результатов ИИ. Реальная ошибка общей симуляции исправляется отдельно и создаёт новый сравнительный baseline.

## 4. Архитектура и интерфейсы

Сохранить `ai_player.gd`, `ai_runtime_coordinator.gd`, `ai_decision_queue.gd` и `ai_planning_task.gd` как границу исполнения. Развивать существующие economy/operations/transport модули небольшими срезами. Новые компоненты вводить только с реальным потребителем:

| Компонент | Ответственность | Основные файлы |
|---|---|---|
| Наблюдение и факты | Законные сведения, происхождение, экономические события, видимые снаряды | `ai_observation_store.gd`, `ai_observation_profile.gd`, новый `ai_belief_model.gd` |
| Карта регионов | Достижимость, проходы, ресурсы, риск маршрута, зоны разведки | `ai_navigation_knowledge.gd`, новый `ai_region_model.gd` |
| Стратегический директор | Выбор целей и планов из нескольких шагов | `ai_strategy_state.gd`, новые `ai_strategy_director.gd`, `ai_plan_library.gd` |
| Экономический план | Спрос во времени, работники, инфраструктура, возраст, исследования | `ai_economy_*.gd`, `ai_plan_budget.gd`, новый `ai_macro_plan.gd` |
| Операции | Назначение армии задачам, сбор, маршруты, подкрепления, отмена | `ai_operations.gd`, `ai_transport_planner.gd` |
| Прогноз столкновения | Быстрая оценка и ограниченное проигрывание вариантов | `ai_combat_model.gd`, новый `ai_combat_predictor.gd` |
| Боевой контроллер | Роли, цели залпов, отход, осада, жрецы, флот | новый `ai_micro_controller.gd` и небольшие стратегии ролей |
| Арена и настройка | Фиксированные соперники, метрики, подбор, проверка обобщения | `benchmark_ai.gd`, `summarize_ai_benchmark.py`, новые инструменты арены |

Общие передаваемые структуры: `ObservationFacts`, `BeliefSummary`, `StrategicPlan`, `EconomicDemand`, `OperationIntent`, `CommandProposal`. Реализовать их отделёнными типизированными данными проекта; ссылки на живой мир запрещены. Предложение команды содержит причину, приоритет, владельца операции, срок актуальности и смету. Отладочная информация удаляется перед записью обычной команды в replay.

Подключение версии: сохранить внешний профиль `skirmish_policy_v1` и существующие ID сложности; в policy добавить явные `algorithm_version` и `capabilities`. Фабрика планировщика выбирает `legacy_adaptive_v1` или `competitive_v2`, а арена отдельно разрешает замороженный `baseline_v1`. До итоговой приёмки обычная новая игра использует прежнюю принятую версию; арена явно включает кандидата. После AI12 переключить default на прошедший champion. Версия алгоритма, набор способностей, параметры и веса записываются в match/save manifest; загрузка не должна молча заменять их новым default. Новая версия становится активной атомарно на создании матча, а не посреди решения. Абляции выполняются явными настройками отдельного запуска. Недействительный/неполный state отклоняется, а не «исправляется» случайным fallback во время партии.

Арбитраж: срочная защита/эвакуация → неотложный микро-приказ → продолжение операции → плановая экономика → разведка. Это приоритет выдачи команд, не безусловное право потратить все ресурсы. Экономические резервы и взаимное исключение задач проверяются общей сметой. Автономная атака движка не должна отменять осмысленный приказ отхода; старый стратегический приказ не должен перезаписывать новый микро-приказ.

Начальные периоды в игровых тактах при 20 Hz: микро 4; операции 10; экономика 20; стратегическое сравнение 80. Событие опасности может запросить более раннее решение на следующей допустимой фиксированной границе. Не увеличивать частоту захвата полного снимка ради каждого юнита: разделить компактные тактические и редкие стратегические данные. Сначала сохранить существующую source/apply семантику, затем доказать эквивалентность расширения.

Начальные вычислительные пределы: 12 стратегических кандидатов, 256 раскрытых узлов плана, глубина 6; для значимого боя до 6 вариантов × 16 шагов по 0,5 секунды; до 64 взвешенных представлений бойцов и 8 целей на бойца на шаг. Представители сохраняют осаду, жрецов и другие редкие роли отдельно. Превышение размера армии приводит к агрегации, не к игнорированию последних ID. Эти значения уточнять только на dev/validation с записью причины.

## 5. Арена, данные и численная приёмка

### 5.1. Фиксированный соперник

AI00 сохраняет исходную политику как `baseline_v1` до изменений алгоритмов. Для совместного матча использовать отдельное пространство скриптов `res://ai_baselines/v1/`, адаптер планировщика и замороженный транзитивный набор алгоритмических зависимостей. При копировании убрать/переименовать глобальные `class_name` и переписать внутренние preload, чтобы не было конфликтов с текущими классами. Разрешённые общие зависимости перечисляются явно: DTO команд, точный codec и авторитетные правила текущей версии. Их хеши входят в series ID. Общие изменяемые AI-helper нельзя считать замороженными.

Самопроверка baseline: не менее 20 сохранённых законных входов с разными экономическими и военными состояниями должны давать прежние команды и прежнее canonical AI state; повторные запуски имеют одинаковые хеши. Эталон фиксируется до правок. Изменение общей симуляции или правил создаёт новую серию, baseline перепроверяется; результаты разных серий не объединяются в доказательство прироста.

### 5.2. Наборы партий

Один базовый случай — полное определение матча, материализованная карта, seed, цивилизации, лимит населения, стартовые ресурсы/возраст, условие победы и фиксированный соперник. Каждый случай имеет две партии со сменой позиций субъектов. Оба ИИ одного paired case играют на той же сохранённой карте; преимущество мест учитывается сменой сторон, а не перегенерацией ландшафта.

| Набор | Базовых случаев | Партий | Использование |
|---|---:|---:|---|
| smoke | 12 | 24 | Быстрая сквозная проверка после крупного среза |
| dev | 48 | 96 | Поиск причин и настройка |
| validation | 64 | 128 | Выбор кандидата и контроль слабых категорий |
| holdout | 64 | 128 | Однократная итоговая оценка против baseline_v1 |
| challenge_holdout | 32 | 64 | Итоговая проверка против специализированных соперников |

Наборы хранить отдельными manifest, без пересекающихся seed между dev/validation/holdout/challenge_holdout. Включить grasslands, narrows, coastal, islands при фактической поддержке текущего генератора; все 16 цивилизаций; обычные ресурсы как основной случай; отдельные high/Bronze варианты; лимиты населения 50/200/500. Не требовать равного числа бессмысленных комбинаций: морской соперник проверяется на подходящей карте. Неудачная генерация — GENERATION_ERROR, а не пропущенный seed. Обнаруженный устаревший fixture исправляется по актуальному контракту с сохранением причины.

Восемь классов соперников: baseline_v1, ранний натиск, стрелковое микро, экономическое развитие, укреплённая оборона, рейды по работникам, осадное наступление, морское давление. У каждого отдельный фиксированный manifest и хеш; все используют обычные цены/туман/команды. Специализированные соперники AI01 — небольшие самостоятельные контроллеры со скриптованными намерениями; они не зависят от ещё не созданных AI04–AI08 и не вызывают будущий код субъекта. Dev/validation покрывают все классы, основной holdout — только baseline_v1, challenge_holdout — остальные семь. Сценарии могут начинаться с заданных симметричных армий для узкой проверки микро, но такие результаты не смешиваются с полноценными партиями с нуля. Командные матчи, специальные победы и нагрузка имеют отдельные наборы.

Основной лимит партии: 36 000 тактов; для островных/командных случаев заранее заданные 72 000. Лимит wall-time устанавливается после 12 калибровочных запусков: max(300 секунд, 3 × измеренный p95 соответствующего размера), не более 3600 секунд на обычную партию. Для длительного stress — отдельный manifest. Отсутствие событий экономики, движения и боя 2400 тактов при незавершённом матче сохраняет checkpoint и даёт STALLED. Легитимное длительное исследование/удержание победы проверяется до объявления STALLED. Обычный предел игровых тактов даёт DRAW_TIME_LIMIT. Wall-time предел даёт INFRA_TIMEOUT; результат не участвует в игровом рейтинге, но входит в отказоустойчивость.

Каждый результат содержит: series/run/case ID, source bundle и policy/opponent hashes, версии симуляции/генератора/наблюдения, карту, seed, настройки, исход, причину завершения, tick, canonical hashes, команды/реплей или путь к нему, метрики и ошибки. `--revision` как произвольной подписи недостаточно. Повтор использует тот же fingerprint; существующий валидный результат переиспользуется. Частичный JSON никогда не считается результатом.

### 5.3. Метрики и критерии

| Область | Обязательная проверка |
|---|---|
| Корректность | 0 утечек скрытого состояния, бесплатных действий, двойных назначений, рассинхронизаций и новых actionable engine errors |
| Команды | Доля неожиданных отклонений <1% на валидных полных партиях; гонки смерти цели/занятия клетки учитываются отдельными причинами и не скрываются |
| Экономика | На контролируемых открытиях median времени Tool/Bronze и выхода на устойчивое производство минимум на 20% лучше baseline по соответствующим применимым показателям; не ухудшить раннюю оборону ради времени возраста |
| Простои | На контролируемом мирном развитии простой работников при доступной работе ≤5%, блокировка производства населением ≤2%; общий простой TC и нехватка пищи показываются также без условной фильтрации |
| Микро | На парных встречах равной исходной стоимости агрегированный ресурсный размен ≥1,20 к прежнему управлению; отдельные обязательные случаи отхода, противоосады и защиты жреца проходят функционально |
| Прогноз боя | На отложенных контролируемых столкновениях точность знака победителя ≥80%; близкие бои показываются отдельно, ошибка потерь сравнивается с текущей формулой |
| Общая сила | На итоговых 128 holdout-партиях против фиксированного baseline score=(W+0,5D)/N ≥0,60 и нижняя 95% граница по seed-блокам >0,50; при недостаточной уверенности писать INCONCLUSIVE |
| Устойчивость | Ни одного краша/безвозвратного зависания в приёмочной выборке; все неигровые сбои перечислены, а не выброшены из отчёта |
| Регрессии категорий | Ни одной новой функциональной невозможности на море/в команде/в условиях победы; ухудшение score категории >0,10 относительно прошлого champion требует разбора и отдельного статуса, а не сокрытия средним |

Численные цели являются критериями, а не уже полученными результатами. Ресурсный размен использует фактическую стоимость с поправкой на цивилизацию; переданное конверсией имущество учитывается один раз, лечение не создаёт фиктивных убийств. Близкий бой для проверки прогноза — различие итоговой сохранённой стоимости <10% начальной суммарной стоимости; показать и полную accuracy, и accuracy вне этой зоны. Никакой ручной разметки «победитель» по предсказанию самого ИИ.

Статистику считать по парным случаям и группам seed, с фиксированным bootstrap seed; не считать две смены сторон независимыми наблюдениями. Wilson допустим как описательный дополнительный интервал бинарных исходов. Ничьи, застревания и инфраструктурные сбои показывать отдельно. Размеры, цивилизации, типы карт и соперников раскладывать по категориям. Сохранённый holdout не используется для подбора весов после просмотра результата.

## 7. Учёт, восстановление и остановка экспериментов

Артефакты запуска: `prototype/qa/ai-competitive/<run_id>/manifest.json`, `events.jsonl`, `cases/`, `checkpoints/`, `replays/`, `reports/`, `release/`. Временные исходные копии и незавершённые файлы — `.tmp/ai-competitive/<run_id>/`. Артефакты не обязаны коммититься. Имена задаются manifest; нельзя искать «последний удачный лог» и подставлять его в новый запуск.

JSON состояния имеет schema_version, plan ID, execution_status, active_task, stages/tasks, evidence, unresolved, next_action. Статусы задачи: pending, in_progress, passed, quality_gap, blocked. Статус этапа passed вычисляется только по его обязательным задачам и приёмке. `quality_gap` не равен passed; общий финальный результат остаётся с пробелами. Для неприменимого элемента конкретной партии использовать capability report, не общий пропуск требуемой функции.

Для зависимостей отдельно хранить functional_gate и quality_gate. Следующий этап может использовать функционально проверенный API при незакрытой численной цели предыдущего; это сохраняет QUALITY_GAP и не разрешает общий COMPLETE. Если нужный API не работает либо не реализован, зависимая задача блокируется, а исполнитель продолжает доступную независимую часть плана. Пройденная функциональная граница не означает, что неудачный кандидат включён в default игры.

На границе задачи сохранять: изменённые файлы/хеши, результат проверок, команды повторения, текущую рабочую гипотезу, известные ошибки и следующий шаг. Атомарная запись: временный файл → валидация → замена. После прерывания проверить файлы/хеши, восстановить первый незавершённый срез и не сбрасывать пройденное. Появившиеся внешние изменения исследовать и включать в новую версию серии; не перезаписывать их старой резервной копией.

Подбор AI10 — конечный бюджет 384 dev-партии + максимум 96 validation-партий. Дополнительные обычные stage-validation выполняются только при изменении кандидата или новой причине проверки. Holdout и challenge_holdout — по одному финальному проходу, суммарно 192 партии; после функционального исправления новые независимые финальные наборы. Не переиспользовать посмотренный holdout как «невиданный». Эксперимент останавливается по заранее заданному числу случаев/поколений, не по удобному проценту побед.

Для внешней человеческой приёмки подготовить локальный пакет, запись партий, скрытые от участников имена вариантов и смену позиций. Рекомендуемая первая серия — 30 paired случаев против нескольких людей разного подтверждённого уровня в этой игре; повторные партии одного человека/seed учитывать как связанные. Не переносить Elo из AoE II или оригинального RoR на этот движок. До данных итоговый human-status остаётся HUMAN_UNMEASURED.
