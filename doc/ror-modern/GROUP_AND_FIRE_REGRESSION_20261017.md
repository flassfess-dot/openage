# Группы после гибели и огонь на башнях

Дата: 2026-10-17.

## Падение

Windows Application Error для `dist/Rise of Rome Prototype/Rise of Rome Prototype.exe`
зафиксировал `0xc0000005`, смещение `0x2d5b8ca`. Соответствующий дамп:
`Rise of Rome Prototype.exe.32932.dmp`. Разбор: `tmp/analyze_group_dump.py`.

В `ControlGroups.recall` значение по умолчанию `Dictionary.get(number, [])`
имело тип Array, но присваивалось Array[int]. Исходный код в минимальном
проекте на том же Windows Release template падает при вызове неназначенной
группы с **тем же кодом и смещением**. Debug сообщает ошибку типа вместо
падения. Сам по себе вызов ранее назначенной и опустевшей группы в этом
минимальном тесте не падает. Почему в конкретном пользовательском матче
сработала ветка отсутствующего номера, по одному дампу не установлено.

Исправление явно копирует ID в принадлежащий группе Array[int]. Главная сцена
проверяет пустой результат до типизированного присваивания. Дополнительно
доступность членов группы проверяется по текущим собственным юнитам симуляции:
прежний overview обновлялся раз в четыре такта и мог сохранять погибших либо
ещё не включать новых юнитов. Это редкая операция по нажатию клавиши; частота
обновления общего обзора не повышается.

`test_destroyed_control_group.gd` вызывает реальный обработчик клавиатуры:
Ctrl+1 → удаление членов игровыми командами → 1 несколько раз → пустая 8 →
Shift+1 с другим выделением → повторное назначение → выбор и центрирование.
Тот же сценарий используется Release entry point
`--verify-control-group-lifecycle --output=<report.json>`.
Минимальный исходный/исправленный Release: `prototype/qa/group-fire-fix-20261017/minimal-repro/`.

## Факелы

В исходных данных римской Watch Tower (79/826) и Sentry Tower (199/821)
составная idle-последовательность имеет шаг около 0.05 секунды. Четыре
огненных слоя используют общий SLP `dethfire`, graphic 324: 20 кадров с
frame_rate=1.0, replay_delay=0. До исправления каждый кадр огня удерживался
секунду. Это задержка выбора кадров, а не недостаток PNG-кадров.

В представлении зданий для общего огненного слоя введён шаг 0.05 секунды.
Это выбранная политика воспроизведения проекта, согласованная с каденсом
составной idle-последовательности; точный executable parity оригинала здесь
не объявляется. Исходный каталог, игровые таймеры и боевые события не меняются.
Огонь использует непрерывное время idle и не перезапускается с каждым выстрелом.
Здания с анимированными слоями не попадают в кэш полностью статических композиций.

`test_building_fire_animation.gd` проверяет обе башни, все четыре слоя,
последовательные шаги 50 мс, переход в AttackWindup и неизменность сырого
каталога. `--verify-tower-fire --output=<report.json>` добавляет настоящую
башню в игровой мир, проводит 40 тактов и сохраняет 40 кадров полного окна.
Проверяется наличие четырёх огней, 20 различных кадров и смена кадра на каждом
такте. Это штатная точка входа приложения, совместимая с Release без --script.

control_groups, destroyed_control_group, building_fire_animation,

graphic_descriptor и game_save_load_pipeline. Журналы: `tmp/group-fire-*`.

`prototype/qa/group-fire-fix-20261017/release-manifest.json`; наличие этого файла
означает, что готовый EXE прошёл оба адресных сценария, а исходники не менялись
между экспортом и проверкой. Сам экспорт не заменяет эти проверки.

Release завершён штатным `tools/ror-full-build.ps1 -VerifyStartup`, журнал
`prototype/qa/dev-scripts/full-build-20261017-180638.log`. Готовый EXE прошёл
случайный матч и save/load, затем оба адресных графических сценария:
packaged-groups passed=true/release=true, packaged-fire passed=true/release=true,
40 кадров, 20 различных фаз огня. Кадры просмотрены, все четыре факела видны.
