## Ближайшие шаги

1. `I0`: переоценить существующие блоки по независимым статусам `FOUNDATION/INTEGRATED/PARITY/HARDENED`; прежнее «проверено» не считать автоматически уровнем parity.
2. `I1`: подтвердить границы авторитетной симуляции, команд, событий, снимков и детерминированного replay.
3. `I2`: подтвердить единый нормализованный каталог и версионированный кеш без runtime-конвертации.
4. `I3`: закрыть интеграционный путь `ввод -> picking -> контекстная команда -> симуляция -> событие -> обратная связь`.
5. Далее двигаться по I4–I13 из `doc/DEVELOPMENT_ROADMAP_ROR_PARITY.md`; задачи U выполнять на соответствующем этапе I10, а не раньше фундаментальных ворот качества.

### Архитектурное решение (2026-09-12, отложенная оптимизация больших армий)

- Оптимизация для будущего лимита населения 500 закреплена за финальным этапом I13 и не меняет текущую очередь функционального соответствия.
- На дальнем перемещении формация использует общий глобальный маршрут/коридор; отдельные участники сохраняют связанные места и решают только локальные расхождения.
- При назначении конкретной цели и в локальном взаимодействии участники получают индивидуальные, но связанные маршруты, сохраняя авторитетное групповое намерение и жизненный цикл формации.
- До I13 допустимы только измерения и минимальные устранения блокирующих просадок; преждевременная замена навигационной архитектуры не выполняется.
- Текущая симуляция уже data-oriented: игровые сущности являются данными, а движение, бой, AI и presentation обслуживаются общими системами; отдельный ECS допускается только после сравнительного профиля.
- Для I13 зафиксирован набор гипотез, а не заранее выбранных переписываний: shared-route/иерархия/flow field, render buckets через текущий Canvas pipeline или `MultiMesh`/RenderingServer, разная частота дорогих систем с интерполяцией, presentation chunk streaming и перенос доказанных CPU-hotspots в GDExtension.
- Camera-dependent редукция работы не может менять simulation tick, replay и исход матча; выгрузка авторитетного мира запрещена. Обязательные ворота измеряют обычный RoR и 500 живых управляемых юнитов на каждого из 2/4/8 игроков (до 4 000 одновременно) на карте ×4 по числу клеток/площади относительно крупнейшей подтверждённой RoR-карты; отдельный stretch использует карту ×4 по ширине и высоте (×16 по числу клеток). Для каждого профиля нужны tick/frame `p50/p95/max`, wall time, path requests, AI/perception, snapshots, allocations, draw calls, RAM/VRAM и не менее 30% `p95` CPU/памяти в резерве.
